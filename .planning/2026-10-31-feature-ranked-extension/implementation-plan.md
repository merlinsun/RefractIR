## Part I. Goal, method, decisions

### Goal

Expose Triton correctness bugs with generated kernels that carry an expected output. The generator is extended feature by feature, in the order the issue tracker's reproducers justify. All local work comes first; the A800 host is then used in one remote phase for the PTX evidence, the exposure checks and the sweeps.

Every Triton issue this project filed, and both the mutation route found, involved a feature or a semantic corner the generator cannot produce. The ranking that matters is by *wrong-result* issues, which F0 establishes from local evidence. The five candidates are Gluon layouts, conversions, dot, scans and nested control flow; F0 may promote `where`/masks or atomics above one of them (Part IV).

### What the local collection records, and what it does not

Each seed file carries the issue URL and, for 267 of 445, the fix PR. The manifest carries a short family label per issue (`fdiv ieee rounding`, `argmax nan interpreter`, …) and a fix status. Neither the issue title nor its labels nor its body are stored locally, so the symptom (wrong result, crash, hang) must be inferred locally from two signals: the family label's words, and the reproducer's own check (a file that asserts or prints an expected value is a wrong-result report; a file that only compiles or launches is a crash report). F0 does this without network access and keeps both signals per issue so the inference can be audited. Fetching issue titles through the GitHub API is an optional enrichment, used only if a token is available; it is not required for D7.

### Method, fixed for every package

- **Path by scalars, values by P0.** A case's path (trip count per loop level, branch outcomes, which lanes a mask covers, which layout is chosen) is realised through scalar `i32` parameters chosen by construction or, where conditions compose, by the existing bit-vector solver. Values come from the probe recipes and LRA steering; the expected output from P0. No lane-level floating-point solving (D3 failed).
- **Contract row before any sweep.** Each new operation gets a row in `docs/tensor-paths-and-fp-contract.md` (specified / pinned / unspecified). The row is drafted locally from the IEEE and Triton documentation and marked *evidence pending*; the PTX evidence is collected in the remote phase before the row is final. Unspecified results get an enclosure or are excluded; nothing is compared with a tolerance.
- **Local verification stops at P0 and the emitted text.** Triton is not importable on the Mac, so the local phase proves each feature through P0, the unit tests, and exact-text tests on the emitted Triton or Gluon source. Compilation, exposure and agreement are proven in the remote phase.
- **Exposure is measured, not assumed.** Every sweep records, per compiled kernel, whether the feature survived to TTGIR/PTX (`mma` encodings for dot, `cvt` for conversions, `scf.if` / nested `scf.for`, scan ops, the declared Gluon layouts).
- **Host and revision.** The A800 host (`n1`, container `triton-build`, two A800-SXM4-40GB, Triton at `/workspace/triton`) runs every sweep on Triton trunk at a revision recorded in the declaration.
- Everything else as before: test-first, clang-format / Ruff, small Conventional Commits on `free-form-regions`, dated declarations with budget and source identity before GPU use, [LOCAL] / [REMOTE-HOST] / [REMOTE-GPU] labels, dated Part III entries.

### Decision rules

- **D7 (after F0, local).** The package order is the rank of the five features by the number of wrong-result issues whose reproducer uses the feature; ties broken by density (wrong-result issues ÷ issues using the feature). A feature outside the five with a wrong-result count above the fifth-ranked one is added at its rank. Crash-only issues are counted separately and reported, not ranked.
- **D8 (start of the remote phase).** Sweeps start only when `make test-tensor` passes on the A800 build, every contract row's PTX evidence is collected, and a 30-minute smoke sweep of the pre-extension generator completes there with every pair agreeing with P0.
- **D9 (per package, remote phase).** A package is complete when its declared sweep shows the feature surviving to compiled code in at least 80 % of admitted kernels and every disagreement has been triaged (candidate reproduced on a fresh checkout of the declared revision, or explained and recorded). Below 80 %, the emission or the builder is fixed and the sweep repeated before the next package's sweep.
- **D10 (escalation).** After two completed packages with at least 8 GPU-hours each and no reproduced candidate, the direction is revisited with the supervisor before the third, with the mutation route's Gluon spike results on the table.

## Part II. Phase L: local work [LOCAL]

### L0. Feature census of the issue reproducers (2 days)

- `test/tensor/campaigns/issue_feature_census.py`, test-first: parse each seed with `ast`; detect features by call names and attributes (`tl.dot`, `dot_scaled`, `.to(tl.<dtype>)` with the target dtype, dtype literals, `cumsum` / `associative_scan`, `atomic_*`, `tl.where`, `tl.range` keywords, nested `For` / `While` depth, `If` inside the kernel, `gluon` imports and `@gluon.jit`, descriptors, `warp_specialize`, math functions). One row per seed with its feature set, its family label and fix status from the manifest, and whether the file is marked an excerpt.
- Symptom inference, local only: `wrong_result` when the family label contains a result word (wrong, incorrect, mismatch, nan, precision, rounding, garbage, result, value) or the file checks a value (`assert`, `allclose`, `testing`, `expected`); `crash` when the label contains assert, segfault, crash, error, compile, verifier, or the file has no value check; `hang` for timeout or hang; `other` otherwise. Both signals are kept per row.
- Optional enrichment: `--github-token` fetches titles and labels and adds a third signal; the ranking is reported with and without it when both exist.
- Output `f0/CENSUS.json` and `f0/CENSUS.md`: per feature, files, wrong-result issues, crash issues, density; the ranked five; features outside the five above the threshold. Apply D7; record the order in Part III.
- Tests: fixture seeds per feature; a nested-loop fixture; a Gluon fixture; the symptom rule on fixed labels and files; the ranking on a synthetic census.

### L1–L5. The feature packages' local parts, in D7 order

Each package's local part is: (1) specification in `docs/SPEC_v0.2.3.md` or the tensor profile notes, (2) profile and P0, (3) emitter with exact-text tests, (4) exporter and builder with the feature as a sampled choice, (5) the contract row marked *evidence pending*, (6) unit tests at every layer, (7) the sweep declaration drafted, with its exposure criterion named. Estimates are for one person, local parts only.

**G. Gluon layouts (2 weeks).** `symirc --target gluon` emits the same SIR body as a `@gluon.jit` kernel with explicit layouts: `BlockedLayout` parameters (`size_per_thread`, `threads_per_warp`, `warps_per_cta`, `order`), `SliceLayout` for reductions, explicit `convert_layout`, and a shared-memory round-trip variant. The layout choice is a sampled path component: one body emitted under K choices, all with P0's expected output. Oracle in the sweep: P0 and agreement across the K choices (the interpreter cannot run Gluon). Written against the Gluon layouts tutorial for Ampere (no TMA, no warp specialisation); the mutation route's Gluon spike, when it reports, replaces any assumption made here. Exposure criterion: the declared layouts appear in TTGIR.

**C. Conversions (1.5 weeks).** A specified narrowing operation in SIR, `tensor narrow <fmt> %x` with `fmt` in `f16`, `bf16`, `e4m3`, `e5m2`: round-to-nearest-even to the format, result kept as an f32 value representable in the format, so SIR's types do not change; saturation and NaN handling as the format defines, to be confirmed against the PTX `cvt` instructions in the remote phase. The emitter converts and widens (`.to(tl.bfloat16).to(tl.float32)`), plus a variant that stores the narrow output and compares its bits. P0 implements the rounding. Exposure criterion: `cvt` instructions in PTX.

**D. Dot (1.5 weeks).** `tensor dot %a, %b` on 2-D tiles. Integer dot first (i8 × i8 → i32, exact, specified; add integer element types to the profile if absent, see `include/ast/tensor.hpp`), then f32 with `input_precision="ieee"`: products specified, accumulation order not, so the output is compared through an enclosure over the K products per lane (the `sum` machinery, extended); tf32 excluded. Exposure criterion: `tt.dot` in TTGIR; f32 with `input_precision="ieee"` lowers through FMA on Ampere, so `mma` encodings need int8 (`i32`) bodies (amended at L1, see Part III).

**S. Scans (1 week).** `tensor cumsum %x, axis`: integer exact; floating point through a per-prefix enclosure (`gamma_(k-1)` for prefix k). P0 sequential. Exposure criterion: scan ops in TTGIR.

**N. Nested control flow and the path planner (2 weeks).** Nested counted loops with parameter bounds and loop-carried tensor state across levels; scalar `if` on comparisons of entry parameters, both arms generated, the path choosing the arm; `while` with an assumed trip bound; per-lane `select` as a path component. The path planner chooses trip counts and branch outcomes, derives the parameter values by construction, and falls back to `symirsolve` when conditions compose. Exposure criterion: nested `scf.for`, `scf.if`, dynamic bounds in TTGIR.
