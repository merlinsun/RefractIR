# Seed export: generated kernels into the layout-mutator harness (phase 2)

Prepared 2026-11-01, branch `free-form-regions` at `bdb93a70`. Companion of layout-mutator's `docs/superpowers/plans/2026-11-01-exact-relations.md` (phase 1). The two share one contract, the `relations.json` sidecar (section 2), and nothing else.

## Part I. Why and what

### Decision

The generated route and the mutation route use one harness. layout-mutator runs and judges every kernel: seeds captured from Triton's tests, issue reproducers, mutants, and from this plan on, kernels generated by RefractIR. RefractIR keeps what only it has: the free-form builder with runtime control flow, the SIR interpreter P0 as an absolute reference, the contract and enclosure analyses. Its sweep driver keeps running the approved feature waves; `compare_p0.py` and `enclose_sweep_bodies.py` also serve as analyses over exported seeds.

The oracle on every run is layout-mutator's relation stage: rewrites of the data, whose expected output transforms (values: a signed power-of-two factor per element; positions: permutation), and rewrites of the schedule, whose expected output is unchanged (launch: options, tile sizes, layout, alignment; code: mutants with the same floating-point dataflow), plus their composite, bitwise, admitted per kernel in the interpreter. For generated kernels two things are better than for real ones: the degrees, parities, reduced axes and operator classes come from the DAG instead of inference, and P0's output is an absolute check that catches a wrong lowering the symmetries cannot see.

### Run, then classify

Admission rules that exist only to make a certificate succeed are removed from the generated route: no exact-input bound, no reduction contract as a refusal, no operator exclusion at build time, no node cap for exactness. Bodies may contain `div`, `exp`, `rem`, any magnitude, runtime and zero trip counts. What happens on a run decides what is compared: the sidecar's class per output, the post-run guards, and the interpreter admission. The builder may be biased toward bodies where more relations apply; it must not be filtered by them.

### Generation without an expected output (decided 2026-11-02)

Reification stays in RefractIR as a generator, not as the oracle. The relations judge every value, so a generated kernel needs only to be valid on its chosen input, not to have an exact P0. Integers decide the path and the addresses: trip counts, loop exits, integer branch conditions, offsets, strides and mask extents, steered by the solver toward corner paths (partial last tiles, zero-trip loops, offset boundaries); validity is otherwise by construction (masked loads, in-range index arithmetic). Floats only flow through the data; a float compared with a literal limits the values relation for that output, which the factor rules already detect. Control flow is structured, as Triton's frontend requires (`for`, `while`, `if`), with data-dependent bounds and exits. This is the next generator plan's subject; this plan only exports what exists.

### What already exists

The 31 October plan's local phase is complete at `64318974`: the census (`.planning/2026-10-31-feature-ranked-extension/f0/CENSUS.md`: dot 30 wrong-result issues, conversions 30, `where` 12, nested control 6, Gluon 4, scans 4), and in SIR, P0, the emitter and the free-form builder: `dot` (i32 exact; f32 with `input_precision="ieee"`), `narrow f16|bf16`, `where`, scalar `if` diamonds with nested loops and a branch parameter, `cumsum`, and per-pair TTGIR feature counts in the sweep. R0 on the V100 (bring-up, PTX evidence for `dot`, `narrow f16`, `narrow bf16`, `cumsum`, the smoke sweep) is approved and pending. This plan exports those bodies; it adds no language feature.

## Part II. The sidecar contract

`relations.json` beside `kernel.py` in a layout-mutator seed directory (`kernel.py`, `launch.json`, `inputs/`, `seed.json`). Identical text in the phase-1 plan, section 1.

```json
{
  "schema": "layout-mutator.relations-sidecar.v1",
  "source": "refractir",
  "inputs":  { "<arg>": { "float": true, "weight": 1, "parity": 1, "permutable_axes": [0],
                         "scale_axes": [0] } },
  "outputs": { "<arg>": { "degree": 1, "parity": 1, "reduced_axes": [], "producer_op": "add",
                          "class": "specified" | "order_dependent" | "excluded",
                          "slice_ops": ["add", "mul", "sum"] } },
  "path":    { "trip_counts": { "n": 4 } },
  "expected": { "p0_sha256": "<hex>" | null, "p0_file": "outputs/<arg>.p0.bin" | null }
}
```

Classes from the contract (`docs/tensor-paths-and-fp-contract.md`): specified = `add`, `sub`, `mul`, `min`, `max`, `rmin`, `rmax`, `where`, `narrow f16`, data movement; `narrow bf16` specified only if R0's PTX row shows one `cvt.rn.bf16.f32` on the host that runs; order_dependent = `sum`, f32 `dot`, f32 `cumsum` (i32 `dot` and `cumsum` are exact, hence specified); excluded = `div`, `exp`, `rem`. Weights and degrees solve the homogeneity equations over the DAG; parity likewise with the dual rules (`min`/`max` swap under negation; a comparison flips). `producer_op` is the operation that writes the output lane, so the zero-sign rule can be exact for generated kernels (zero by value only when the producer is `add` or `sub`).

## Part III. Work packages [LOCAL unless marked]

### E0. Census

Done on 31 October (`2affe9f2`, `f0/CENSUS.md`); its order is used in E4 to choose which feature blocks to export first.

### E1. Exporter (3 days)

`test/lib/tensor_seed_export.py`: from a free-form region bundle (SIR, `region.json`, the emitted `kernel.py` from `symirc`, the probe inputs, the scalar parameters including the trip parameter), write a layout-mutator seed directory: `kernel.py` unchanged, `launch.json` with every tensor argument as a `raw` input and scalars by value, `inputs/` with the bytes, `seed.json` with provenance (seed number, commit, exporter flags), and the sidecar with `expected` empty. Tests: a fixture bundle round-trips through layout-mutator's `seeds.format` loader (vendored test copy or a pinned import); every tensor's shape, dtype and strides match the bundle; the trip parameter is an `i32` scalar argument.

### E2. Sidecar analysis (3 days)

`test/lib/tensor_relations_sidecar.py`: over `region.json`'s DAG, per output: `slice_ops`, `class`, `reduced_axes`, `producer_op`; weights and degrees from the homogeneity equations (integer solve; `null` when only trivial); parities with the dual rules; `permutable_axes` per input (axes no reduction in its forward slice consumes). `scale_axes` per input for mixed scaling (added 2026-11-02): axes along which the exponent rules of the exact-relations plan let its exponent vary per index; the exporter may also lift literals to parameters so they scale. Reuse the DAG walk of `tensor_enclosure.py`. Tests: a pointwise body (degree 1, parity 1, all axes permutable); a product body (degree 2, parity 0); a mixed `a·b + c` body (weights 1, 1, 2); a `min`/`max` body (dual parity); a `sum` body (order_dependent, reduced axis); a `div` body (excluded output, other outputs still specified).

### E3. P0 expected outputs (2 days)

For each exported input, run `symiri` and write `outputs/<arg>.p0.bin` and its SHA-256 into `expected`; a P0 refusal (non-finite, UB) leaves `expected` null with the reason in `seed.json`. Tests: the hash matches a direct `symiri` run; a planted overflow yields `null` with `p0_ub`.

### E4. Batch export (2 days)

`test/tensor/campaigns/export_seed_block.py`: a seed block through the existing builder with `--trip-parameter` and, per block, one of the feature flags that already exist (`dot`, `narrow`, `where`, `--branch-parameter` with `--outer-trips`, `scan`), every admission rule that exists only for certification switched off (`--exact-input-bound` absent, no contract refusal, node cap raised to the compiler's limit), probes I0, I3 and the corner recipes, optional steered inputs, one seed directory per body, inputs as named variants the harness can select. Blocks in census order: dot, narrow, where, nested, scan. Record each block's digest. Tests: a block of 8 seeds exports 8 directories with sidecars and P0 hashes; a refused body (builder failure, not numerical) is logged, not exported.

### E5. Validation on the host [REMOTE-HOST, then REMOTE-GPU inside phase 1's declared run]

Export the W4d block (`31000000`–`31000287`) and hand the directory to the layout-mutator session as seed set (d) for the phase-1 run; expected: admission near 100 % on specified outputs (the DAG says what the interpreter would otherwise have to discover), zero violations on bodies that agreed in W4d, and P0's hash equal to the GPU output wherever `expected` is set. Any disagreement here is a defect in E1–E3 or in the sidecar rules before it is anything else.

### E6. Cross-oracle comparison (2 days, after both runs)

`test/tensor/campaigns/compare_oracles.py`: joins a wave's sweep records with the layout-mutator rows of the same exported bodies by seed number and input; per body and output, the verdict of each oracle (P0 and enclosure under the sweep; relations C/N/S/P/X, P0 hash and tolerance signal under the campaign); a table of agreements and of candidates seen by one side only, each with its lane record. Tests on fixture records. This is the measurement the two harnesses are kept for.

### Relation to R0 and the waves

R0 proceeds as approved; its PTX rows fix the sidecar classes for `narrow bf16`, f32 `dot` and `cumsum` on the host that runs. The 31 October plan's waves 1 and 2 (RefractIR-driven feature sweeps) stay, by Merlin's decision of 2026-11-01. E4 exports the same feature blocks, so each block runs twice: under RefractIR's driver with P0 and the enclosures, and inside layout-mutator's campaign with the relation stage and P0's hash. The two reports are compared kernel by kernel: candidates found by one oracle and not the other are the measurement this plan exists for. Gluon excluded.
